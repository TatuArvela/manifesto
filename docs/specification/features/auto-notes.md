# Auto-notes

Auto-notes are cards generated by small user-supplied JavaScript plugins rather than typed by hand. A plugin runs on every refresh and returns one or more notes, so the card always shows a current answer: days until a date, whose turn it is this week, how far through the year we are.

Nothing an auto-note produces is stored as a note. The plugin source is the source of truth, and the cards are recomputed from it.

## Behavior

- Auto-notes appear in the **Auto-notes** view (`/auto-notes`) and alongside ordinary notes in the other views, subject to the usual filters.
- Their title and content are read-only. A generated card cannot be edited, because the next run would overwrite the edit.
- Everything else about the card is the user's: colour, pinning, tags, archiving, trashing and reminders can all be changed, and those changes persist across runs (see [Overrides](#overrides)).
- A card carries a refresh control that re-runs the plugins on demand.
- A plugin that throws does not disappear silently: its card is replaced by an error note titled `⚠ <plugin name>` containing the message, and the same message is stored on the plugin so the management UI can show it.
- Plugins are managed in **Settings → Auto-notes**: add, enable/disable, refetch a URL plugin, or remove.

### When plugins re-run

There is no polling timer. All enabled plugins re-run when:

- the app mounts,
- the plugin list changes (added, removed, enabled, disabled, refetched),
- the locale changes, or
- the user asks for a refresh from a card.

Runs are serialized: a refresh requested while a run is in flight is queued and coalesced into a single re-run rather than overlapping it.

## Plugin Format

A plugin is a plain JavaScript source string, not a module. It has two requirements.

**A title directive.** The first non-empty line must be a `// @title <name>` comment; anything else is rejected with `MissingTitleError`. Keeping the name in the source means a plugin cannot end up mislabeled after a paste or a refetch.

**A `_default` assignment.** The sandbox looks for a global `_default`, which is either one function or an array of functions. Each function is called with the plugin context and returns a note or an array of notes.

```js
// @title Year progress

function yearProgress({ today, locale, stdlib }) {
  return { title: "Year progress", content: "…", color: "green" };
}

_default = yearProgress;
```

### Plugin context

Each function receives one `ctx` argument:

| Field | Type | Description |
| --- | --- | --- |
| `today` | `string` | The current moment as an ISO 8601 timestamp, from `new Date().toISOString()`. Fixed for the whole run, so every plugin in one pass sees the same clock. |
| `locale` | `string` | The active UI locale (`"en"`, `"fi"`, …). |
| `stdlib` | `object` | Date helpers, with the locale and the translated relative-time labels already bound. |

### Standard library

`ctx.stdlib` exposes `addDays`, `daysBetween`, `firstFuture`, `lastPast`, `lastOccurrence`, `formatDate`, `formatDateTime`, `relativeDays` and `approxUntil`. They are serialized into the sandbox as source and rebound there, so a plugin gets working date maths without the app exposing anything else of itself.

`approxUntil` and `relativeDays` render phrases like "in two weeks" using the app's own message catalogue, which is why a locale change re-runs every plugin.

### Returned notes

A function returns one note object or an array of them; a plugin exporting several functions returns one per function. The result is flattened, so an array of arrays is accepted rather than refused.

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `title` | `string` | yes | Rejected if missing or not a string. |
| `content` | `string` | yes | Markdown. Rejected if missing or not a string. |
| `color` | `NoteColor` | no | Must be a known colour name, else dropped. |
| `font` | `NoteFont` | no | Must be a known font name, else dropped. |
| `pinned` | `boolean` | no | |
| `tags` | `string[]` | no | Non-string entries are dropped; capped at 50 to match the server's limit. |
| `position` | `number` | no | Must be finite. Defaults place auto-notes ahead of ordinary notes. |
| `key` | `string` | no | A stable sub-id, so a plugin returning several notes keeps each one's overrides across runs. |

`title` and `content` are strict because a note without them is not a note. Every optional field is lenient: a bad value is dropped rather than failing the run, since one misspelled colour should not cost a plugin its whole output.

## Execution and Sandboxing

Auto-notes run code the user pasted in, so the plugin executes at three removes from the app, and each remove does a distinct job.

1. **An iframe with an opaque origin.** `public/autonotes-sandbox.html` is loaded through `iframe.src` with `sandbox="allow-scripts"` and no `allow-same-origin`, so the frame reaches no host storage, cookies or DOM. It cannot be a `srcdoc` frame: those inherit the host's `script-src 'self'`, while a frame loaded from a real URL carries its own CSP and can permit the `unsafe-eval` a plugin needs without relaxing the app's.
2. **A blob Worker inside the frame.** This is what makes the two-second timeout enforceable: a plugin that never returns occupies only the worker's thread, so the timer still fires and tearing down the frame takes the worker with it. An engine that refuses a worker at an opaque origin falls back to running on the frame's thread; the fallback is reported in the frame's `init-ok` message and warned about by the host, because on that path a `while (true)` blocks the page and the timeout cannot be enforced.
3. **Validation on the host side.** The frame returns `JSON.stringify({ value })` and deliberately validates nothing. The check belongs outside the sandbox: a plugin that has subverted its frame would satisfy any check the frame made about itself.

The host–frame protocol is: the frame posts `sandbox-booted`, the host replies with `init` carrying the standard-library prelude, the frame evaluates it, starts its worker and posts `init-ok`; each invocation is then a `run` message answered by `run-ok` or `run-err`.

## Plugin Sources

A plugin has one of two origins:

- **Inline**: source pasted into Settings, stored as-is.
- **URL**: fetched from an HTTPS URL. The fetched source is cached with the timestamp it was retrieved, so plugins work offline; **Refetch** pulls the current version and re-reads the title from it.

A URL plugin is fetched, not linked: an edit at the far end does not reach an existing installation until it is refetched.

## Data Model

Plugins live in `localStorage` under `manifesto:auto-notes`, each as a `PluginSource`:

- `id`: local identifier
- `name`: from the `// @title` directive
- `enabled`: disabled plugins are skipped
- `origin`: `{ kind: "inline", source }` or `{ kind: "url", url, fetchedAt, source }`
- `lastError`: the message from the most recent failed run, if any

A generated note is an ordinary `Note` assembled in memory, with:

- `id`: `generated:<pluginId>:<key or index>`
- `readonly`: `true`
- `source`: `{ kind: "auto-note", pluginId, noteKey }`

### Overrides

User changes to a generated card are stored separately, in `localStorage` under `manifesto:auto-note-overrides`, keyed by the generated note's id and merged in as the note is rendered. An override may carry `color`, `pinned`, `tags`, `archived`, `trashed`, `trashedAt`, `reminder` and `position`.

Because the plugin owns the content, "permanently delete" on an auto-note clears its override instead of deleting anything: the card returns on the next run in its default state. To stop a card appearing at all, disable or remove its plugin.

## Limits

| Limit | Value |
| --- | --- |
| Plugin run timeout | 2 seconds |
| Notes per plugin run | 100 |
| Tags per generated note | 50 |
| Plugin source size | 256 KB |

## Limitations

- Auto-notes are local to the device: plugins, overrides and generated cards are never sent to the server, and a plugin added on one device does not appear on another.
- Generated notes are not written to storage, so they are absent from exports and from version history.
- Title and content cannot be edited; the plugin is the only way to change them.
- The two-second timeout cannot be enforced on engines that refuse a Worker at an opaque origin (the host warns when it detects this).
